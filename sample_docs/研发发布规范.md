# 星河科技研发发布规范

## 分支与评审

所有代码变更必须从短生命周期功能分支发起 Pull Request。合并到主分支前至少需要一名非作者研发人员批准；涉及支付、权限或数据库迁移的变更需要两名评审者，其中一名必须是模块负责人。禁止直接向主分支推送代码。

## 自动化检查

Pull Request 必须通过单元测试、静态检查、依赖漏洞扫描和构建检查。测试失败时不得使用管理员权限绕过。紧急修复可以缩短评审等待时间，但不能跳过自动化检查和事后复盘。

## 发布流程

常规发布按“开发环境验证—测试环境验收—预生产冒烟—生产灰度—全量发布”顺序执行。发布负责人应在变更单中填写版本号、影响范围、验证步骤和回滚方案。生产灰度首先覆盖 5% 流量，观察 20 分钟核心指标无异常后扩大到 25%，再次观察 20 分钟后方可全量。

## 回滚和事故

错误率超过基线两个百分点、关键接口 P95 延迟增加 50%，或出现数据一致性风险时必须停止发布并执行回滚。一级事故应在五分钟内通知值班负责人，十五分钟内建立事故频道，每三十分钟同步一次进展，并在事故结束后两个工作日内完成无责复盘。

## 密钥和数据库

密钥只能保存在公司批准的密钥管理服务中，不得写入源代码、镜像或构建日志。数据库结构变更必须提供向前与向后兼容方案；破坏性迁移应拆成至少两个版本发布，不得在业务高峰期直接删除字段。
